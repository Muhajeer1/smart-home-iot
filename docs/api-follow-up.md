# Улучшения API после переноса фронтенда

Статус: **заметки и предложения; сервер в рамках миграции не меняем**.

Цель — закрыть реальные пробелы сценариев после завершения React-фронтенда. Отсутствие кнопки не всегда означает дефект: для истории измерений и журнала событий важна сохранность исходных данных. Ниже отдельно указано, что уже можно сделать через API, а где нужен новый контракт и решение о правах.

## Карта действий по сущностям

| Сущность | Что предоставляет текущий API | Что переносим / улучшаем в React | Что требует сервера |
| --- | --- | --- | --- |
| Дом | Свои дома, создание, редактирование своим владельцем, удаление | Формы, поиск, подтверждение удаления, прямые ссылки | Предпросмотр последствий удаления; согласовать права техника и администратора |
| Комната | Список по дому, создание, редактирование | Формы с валидацией, поиск, переход к устройствам | Удаление комнаты; решение, что делать с устройствами и историей |
| Устройство | Список по комнате, создание с сенсорами, редактирование модели/состояния для admin/technician, удаление | Фильтры, формы, подтверждение, описание сенсоров | Понятное пользовательское имя, перемещение между комнатами; отдельные права на свойства и состояние |
| Сенсор | Чтение по устройству, добавление недостающих стандартных сенсоров через устройство | Поиск, конфигурация, переход к истории, нормальный диапазон и enabled/disabled | Изменение диапазона, включение/отключение, ручное добавление и удаление; существующие методы контроллера create/delete не подключены к маршрутам |
| Показание | Чтение по сенсору, одиночная и глобальная пакетная симуляция для admin/technician | График, даты, качество, выход за диапазон, сортировка, страницы и CSV | Серверные фильтры/пагинация/агрегации; при необходимости корректировки — аудит и причина, а не молчаливая перезапись |
| Тревога | Список, resolve/reopen, удаление | Состояния, resolve/reopen и подтверждение удаления перенесены | Причина/комментарий закрытия; автозакрытие при восстановлении; история изменений |
| Событие | Список общий или по дому | Безопасный вывод текста, поиск и фильтры | Серверная фильтрация/пагинация; обычное редактирование/удаление не предлагается |
| Пользователь | Вход/регистрация/выход, текущий профиль; admin: список и удаление | Список/поиск/удаление перенесены; защита собственного аккаунта в UI | Изменение профиля/пароля; admin: роли/блокировка; защита последнего администратора |

## Предлагаемый порядок после миграции

### P1 — надёжность и согласованные права

1. **Единая матрица доступа.** Сейчас `DELETE /homes/:id` допускает техника к чужим домам, а `PUT /homes/:id` ограничен владельцем независимо от роли. Описать правила для каждой операции и проверить их на сервере. Источник: `controllers/homeController.js`, `routes/homeRoutes.js`.
2. **Изоляция истории событий.** `GET /events/home/:homeId` требует сессию, но обработчик не ограничивает запрос владельцем дома. Добавить проверку доступа и тест чужого дома. Источник: `controllers/eventController.js`, `routes/eventRoutes.js`.
3. **Освобождение соединения.** Стартовый `db.connect(callback)` не возвращает полученное соединение пулу. Исправить освобождение и обработку недоступной БД. Источник: `db.js`.
4. **Атомарность показания, события и тревоги.** Одиночная запись показания и сопутствующие действия идут раздельно; сервисы событий/тревог подавляют ошибки. Определить, какие операции должны быть в транзакции. Источник: `controllers/readingController.js`, `services/eventService.js`, `services/alertService.js`.
5. **Повторные запросы и конкуренция.** Дедупликация активных тревог и стандартных сенсоров использует чтение перед вставкой. Проверить фактические ограничения БД; предусмотреть уникальные ограничения/идемпотентность. После потери ответа клиент не должен создавать дубликаты. Источник: `services/alertService.js`, `controllers/deviceController.js`.

### P2 — отсутствующие действия с сущностями

6. **Удаление комнаты.** Предлагаемый `DELETE /rooms/:id`. Перед реализацией выбрать политику: запрет при наличии устройств либо явное каскадное удаление. Полезен endpoint предварительного подсчёта затрагиваемых устройств/сенсоров/показаний. Критерии: права, понятные ошибки, подтверждение, корректные счётчики, сохранность незатронутых данных.
7. **Редактирование сенсора.** Предлагаемый `PATCH /sensors/:id` для `normal_min`, `normal_max`, `is_active`. Строгая проверка чисел, min ≤ max, явный смысл отсутствующей границы, права по устройству. Изменение единицы или типа после накопления измерений должно иметь отдельную политику.
8. **Ручные сенсоры и удаление.** Решить, нужны ли пользовательские сенсоры сверх стандартных. Не подключать имеющиеся контроллеры create/delete без проверки прав: сейчас они не имеют маршрутов и не обеспечивают полный контракт владения. Архивация предпочтительна, если история должна сохраняться.
9. **Свойства устройства.** Пользовательское имя отдельно от модели; перенос в другую комнату того же дома с проверкой доступа. Смена типа затрагивает состав сенсоров и историю, поэтому не должна становиться обычным свободным полем.
10. **Профиль и управление учётными записями.** Имя/email/смена пароля, блокировка вместо необратимого удаления, назначение ролей администратором. Уточнить поведение сессий после смены пароля/роли и запрет удаления последнего администратора.

### P2 — история и симуляция

11. **Серверная пагинация и фильтры показаний.** Сейчас `GET /readings/:sensorId` возвращает всю историю. React разбивает уже загруженный массив на страницы — это уменьшает DOM, но не трафик. Нужны `from`, `to`, `quality`, сортировка и cursor/limit; стабильный порядок `(reading_time, reading_id)`. Отдельные total/statistics нужны, чтобы график и сводка не считались по одной странице.
12. **Пакетная симуляция с выбранной областью.** Сейчас `/readings/simulate-bulk` использует все сенсоры, независимо от выбранного дома. Добавить `home_id`/`device_id`/список сенсоров и серверные права. Валидировать именно целое число 1–50000: существующая проверка допускает дроби, а числовой 0 подменяется значением по умолчанию. Для больших запусков рассмотреть фоновые задачи и статус выполнения.
13. **Правдоподобные данные симулятора.** Для `motion`/`open_close` генератор сейчас применяет общий непрерывный диапазон и может выдавать дробные значения. Нужны правила бинарных сенсоров, корректные единицы, допустимые физические диапазоны. Согласовать применение `is_active` и состояния устройства: текущие запросы симуляции их не отфильтровывают.
14. **Разделить качество и нормальность.** Quality flag и сравнение значения с диапазоном — разные признаки. React показывает их отдельно. На сервере нужно определить бизнес-смысл флага, когда создаётся тревога, как изменяется severity и что происходит при изменении нормальных границ. Исторические результаты сейчас сравниваются с текущими границами, а не с границами на момент записи.
15. **Происхождение данных и исправления.** У показания нет показанного в API признака real/simulated. Полезны `source`, автор операции, причина корректировки и неизменяемое исходное значение. Редактирование и удаление истории обсуждать только вместе с этим контрактом и политикой хранения.

### P3 — удобство и масштабирование

16. **Прямые scoped detail endpoints.** Сейчас для проверки URL-иерархии React загружает списки родителей. `GET /homes/:id`, `/rooms/:id` и `/devices/:id` в отдельном API namespace с контекстом родителя сократят запросы и помогут общим рабочим областям admin/technician. Существующие GET-пути комнат/устройств уже означают список по родителю; их семантику нельзя незаметно заменить.
17. **Поиск, пагинация и экспорт событий/тревог.** Единый контракт фильтров, дата/время, выбранный дом и статусы. Экспорт большого объёма должен выполняться сервером с теми же правами и фильтрами.
18. **Жизненный цикл тревоги.** Решить: сохраняется ли тревога после возвращения устройства online/нормального показания, кто её подтверждает, как выглядит повторное срабатывание. Добавить журнал действий и различать resolve, acknowledge и delete, если это нужно пользователям.

## Дополнения после переноса панелей и аналитики

19. **P1 — серверная защита администратора и минимальный ответ.** DELETE /admin/users/:id сейчас не запрещает удаление себя/последнего администратора; RETURNING * возвращает в JSON также password_hash. Нужны серверная проверка с учётом конкуренции и явный список публичных полей. React блокирует опасные действия по загруженному списку и не использует тело ответа удаления, но это не заменяет серверную защиту. Источник: controllers/adminController.js.
20. **P2 — контекст в глобальных списках.** Добавить home_id/room_id/device_id там, где сейчас есть только названия: admin/devices, technician/devices, technician/sensors и аналитика. Это позволит открывать точные детали из системных списков, не угадывая ID по неуникальным названиям. Возвращать полную согласованную DTO после обновления тревоги/устройства; сейчас React объединяет raw-ответ с предыдущей строкой.
21. **P2 — смысл аналитики и единицы.** latest/average/abnormal отчёты не возвращают unit. Добавить единицы, группировку среднего по совместимым типу и единице, стабильный выбор последнего reading по (reading_time, reading_id): текущий MAX(time) может дать две строки одного сенсора. Согласовать временной диапазон и сортировку всех отчётов. React явно подписывает 30 дней только для alert-summary.
22. **P2 — последствия удаления.** Для admin/users, homes, devices нужен единый контракт предварительного подсчёта затрагиваемых записей и политика ограничения/каскада/архивирования. Сейчас подтверждение говорит о возможном удалении связанных данных без выдуманного точного числа; реальные разрушительные операции в проверке не выполнялись.
23. **P3 — разрешение тревоги и история.** GET /alerts не возвращает resolved_at, хотя операция его записывает. Полезны resolved_at, resolved_by, причина, а также стабильная пагинация. Перевод устройства в active автоматически не закрывает уже созданные тревоги; интерфейс объясняет это при смене статуса.

## Уже улучшено без изменений API

- Последовательные модальные формы вместо prompt, сохранение черновика при ошибке, блокировка повторной отправки.
- Подтверждение удаления дома/устройства, понятная кнопка отмены, клавиатурный фокус.
- Прямые URL и проверка принадлежности комнаты/устройства/сенсора родителю перед чтением потомков.
- Поиск и фильтры для домов, комнат, устройств и сенсоров.
- История: сводка, график, диапазон дат в локальном времени, фильтры quality/range, сортировка, страницы, CSV всей отфильтрованной выборки.
- Раздельное отображение качества показания и выхода за текущий нормальный диапазон.
- Отдельный операторский симулятор. Глобальная пакетная операция имеет явное описание области и подтверждение; обычному пользователю недоступна.

- Поиск/фильтры/пагинация событий, тревог и глобальных каталогов, безопасный текст без innerHTML.
- Resolve/reopen тревог и подтверждения удаления; сохранение названий дома/комнаты после ответа сервера.
- Шесть аналитических отчётов с независимыми ошибками и отменой устаревших запросов при смене дома.
- Панели администратора и техника, меню по роли, явный системный масштаб данных, защита своего аккаунта от удаления в UI.

Перенос существующих разделов фронтенда завершён; переключение основного запуска и публикации остаётся отдельным шагом. Пункты API выше — предложения, а не уже реализованные серверные возможности.
